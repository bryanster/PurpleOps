# Azure Container Apps (Terraform)

A fully worked Terraform example that deploys Blacklight to
[Azure Container Apps](https://learn.microsoft.com/azure/container-apps/) — Azure's serverless
container service, the Azure equivalent of "Cloud Run".

What it provisions:

| Resource | Purpose |
|---|---|
| Container App (single replica) | Runs the published `ghcr.io/bryanster/blacklight` image |
| Storage Account + Azure Files share | Persistent `/var/lib/blacklight` — the DuckDB database, its WAL and uploaded evidence |
| Key Vault | Holds `BLACKLIGHT_SESSION_SECRET`, `BLACKLIGHT_ENCRYPTION_KEY` and — if you ask for a first administrator — that account's initial password, all generated by Terraform and stored nowhere else |
| User-assigned managed identity | Lets the app read the Key Vault secrets |
| Log Analytics workspace + Container Apps environment | Required base for Container Apps |

The app's two secrets are generated with the `random` provider, stored in Key Vault, and referenced
by the container app through a managed identity — the values never appear in the container app's own
secret list. The only input required from you is an Azure sign-in.

They also never reach the Terraform state file. The generators are
[ephemeral resources](https://developer.hashicorp.com/terraform/language/resources/ephemeral) — they
exist for the duration of one operation and are not persisted — and they feed
`azurerm_key_vault_secret.value_wo`, a
[write-only argument](https://developer.hashicorp.com/terraform/language/resources/ephemeral/write-only)
the provider sends to Azure without Terraform recording it in state or in the plan file. Key Vault is
the only place `BLACKLIGHT_SESSION_SECRET` and `BLACKLIGHT_ENCRYPTION_KEY` exist.

There is a one-click equivalent of all of this in [`deploy/azure-arm/`](../azure-arm/README.md) — the
same resources as an ARM template behind a **Deploy to Azure** button, with no Terraform to install
and no state to keep. Use it for a first deployment or a demo; use this for anything with a
lifecycle, where planning a change before making it and keeping the secrets out of the deployment
entirely are worth a state file.

## Prerequisites

- [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli), signed in: `az login`.
- [Terraform](https://developer.hashicorp.com/terraform/install) ≥ 1.11 (write-only arguments).
- A subscription where you can create resource groups, set Key Vault access policies, and register
  resource providers (Owner, or Contributor with those rights).

The dev container ships both CLIs, so from inside it only `az login` is left to do.

The first apply registers the `Microsoft.App`, `Microsoft.OperationalInsights` and
`Microsoft.Storage` providers if your account can. To do it once up front:

```sh
az provider register --namespace Microsoft.App
az provider register --namespace Microsoft.OperationalInsights
az provider register --namespace Microsoft.Storage
```

## Deploy

```sh
cd deploy/azure-terraform
az login
terraform init
terraform apply
```

`terraform apply` creates everything and prints the URL:

```
app_url = "https://blacklight.<env>.<region>.azurecontainerapps.io"
```

Copy `terraform.tfvars.example` to `terraform.tfvars` first if you want to change the region, app
name, image tag, or container size.

## Create the first administrator

A fresh deployment has no users and no sign-up (see `docs/deploy.md`), so something has to create the
first account. There are two ways, and on Container Apps the first is much less work.

### From Terraform (recommended here)

Set `admin_email` and apply:

```sh
terraform apply -var admin_email=you@example.com -var admin_name="Your Name"
```

Terraform generates a password, stores it in Key Vault write-only beside the other two secrets, and
passes the address, the name and the password to the app. The app creates that account — as a
platform administrator, active, with a local password — **the first time it starts against a database
with no accounts in it**, and ignores the setting on every start afterwards.

Read the password out of Key Vault and sign in:

```sh
$(terraform output -raw admin_password_command)
```

Change the password at first sign-in. Terraform cannot print it directly: the value is write-only, so
it exists in Key Vault and nowhere else — not in state, not in the plan.

Two things worth being clear about:

- **It is a bootstrap, not an account manager.** The app acts on these variables only when there are
  no accounts at all. It cannot reset a password, re-promote an account somebody demoted, or revive
  one somebody disabled — that is what makes it safe to leave `admin_email` set for the life of the
  deployment. Bumping `admin_password_version` stores a new password in Key Vault and changes nothing
  about the account; a genuinely forgotten password is a `blctl` job, below.
- **The password reaches the app as an environment variable.** This deployment uses
  `BLACKLIGHT_BOOTSTRAP_ADMIN_PASSWORD`; the application also accepts
  `BLACKLIGHT_BOOTSTRAP_ADMIN_PASSWORD_FILE`, which is the better of the two, but the `volume` block
  in the azurerm version pinned here takes only `AzureFile` and `EmptyDir`, so a secret cannot be
  mounted as a file from this configuration. The revision holds a *reference* to the Key Vault
  secret rather than the value, and the value is in the replica's process environment. Change the
  password at first sign-in, and clear `admin_email` and apply again if you want the variable off
  the revision entirely.

To supply your own password instead of a generated one, keep it out of state with an ephemeral
variable:

```sh
TF_VAR_admin_password='…' terraform apply -var admin_email=you@example.com
```

### With `blctl`

The other way, and the only one on a deployment you would rather not hand a password to: `blctl user
create` needs exclusive access to the database — DuckDB gives the file to one process at a time. On
Container Apps that means stopping the app, running `blctl` once against the same file share, and
starting it again:

```sh
# 1. Stop the app (scale to zero), releasing the database lock.
az containerapp update --name blacklight --resource-group blacklight-rg \
  --min-replicas 0 --max-replicas 0

# 2. Run blctl once in any container that mounts the same share at /var/lib/blacklight.
#    A one-off Container Apps Job in the same environment is the cleanest way
#    (see "Use storage mounts" and "Jobs" in the Container Apps docs). The command is:
printf '%s' "$PASSWORD" | blctl user create --email you@example.com --name "Your Name" --admin

# 3. Bring the app back to its single replica.
az containerapp update --name blacklight --resource-group blacklight-rg \
  --min-replicas 1 --max-replicas 1
```

The resource group and app name are `name` and `name-rg` from `variables.tf` — `blacklight` and
`blacklight-rg` by default.

## Secrets: rotation, and bringing your own

Because the stored value is write-only, Terraform cannot see it and so cannot diff it. Rotation is
driven by a counter instead — `session_secret_version` and `encryption_key_version`, both `1` by
default. Bump one and the next apply writes a new version of that Key Vault secret; leave them alone
and applies never touch the stored values:

```sh
terraform apply -var session_secret_version=2   # new session secret: signs everybody out
```

Container Apps caches Key Vault references, so give the app a new revision to pick the value up
(`az containerapp revision restart`, or any apply that changes the template).

Rotating `encryption_key_version` is destructive: the encryption key protects enrolled MFA
authenticators, recovery codes and service tokens, and changing it makes all of them unreadable.
Only do it as part of a deliberate re-enrollment.

You can also supply the values yourself, through the `session_secret` and `encryption_key` variables.
Both are `ephemeral`, so they are used during the run and never persisted — pass them with `-var`,
`TF_VAR_session_secret`, or a tfvars file you keep out of version control (`.gitignore` already
excludes `*.tfvars`):

```sh
TF_VAR_session_secret="$(openssl rand -hex 32)" terraform apply
```

Supplied values are subject to the same rule as generated ones: they are written only when the
matching version counter changes.

**Adopting a deployment created before this config went write-only.** Earlier revisions of this
example stored both secrets with `azurerm_key_vault_secret.value`, which put them in state. The first
apply after upgrading rewrites both Key Vault secrets — with freshly generated values unless you hand
back the current ones, which would invalidate every MFA enrolment. To keep them:

```sh
kv=$(terraform output -raw key_vault_name)
TF_VAR_session_secret=$(az keyvault secret show --vault-name "$kv" --name blacklight-session-secret --query value -o tsv) \
TF_VAR_encryption_key=$(az keyvault secret show --vault-name "$kv" --name blacklight-encryption-key --query value -o tsv) \
  terraform apply
```

Older state versions still hold the plaintext from those earlier applies — the upgrade does not
scrub state history, so treat existing state snapshots (and any remote-state backups) as sensitive.

## Backups and upgrades

`blctl backup` and `blctl migrate` have the same single-process constraint: stop the app, run the
command against the same share, start it again. Back up the Key Vault secrets too — the session
secret and encryption key live there and nowhere else (not in the container, not in Terraform state),
and a restored database without its encryption key is one where nobody with MFA can sign in.

To upgrade, change `image_tag` and run `terraform apply`.

## Caveats

- **Single replica is load-bearing.** DuckDB allows one process per database file, so the app is
  pinned to `min_replicas = max_replicas = 1`. Do not scale it out — a second replica would contend
  for the shared database.
- **DuckDB on a network filesystem.** Azure Files (SMB) is a managed, network-attached filesystem;
  DuckDB is designed for local disks and discourages database files on network filesystems. The
  single-replica constraint keeps the access pattern to one exclusive holder, which is the same
  assumption the compose deployment makes on a named volume. For heavy or latency-sensitive use,
  test before trusting it in production.
- **`/dev/shm` is an EmptyDir mount.** Container Apps fixes `/dev/shm` at 64 MiB, which starves
  Chromium during PDF rendering. The example mounts an EmptyDir over `/dev/shm` to give it the
  replica's ephemeral disk instead.
- **No scale-to-zero.** The app runs with a minimum of one replica because the database is stateful
  and single-writer, so there is always an instance running (and billed).
- **The app secrets are not in Terraform state — the storage account key still is.** The session
  secret and encryption key are generated ephemerally and written write-only, so they live in Key
  Vault only. The Azure Files share, though, is mounted with a storage account key, and `azurerm`
  reads that key into `azurerm_storage_account`'s state attributes; Container Apps SMB mounts have no
  managed-identity equivalent. State remains sensitive for that reason, and is worth keeping in a
  backend with encryption and access control (`az storage account keys renew` rotates the key, but
  needs an apply afterwards to re-point the mount).

## Teardown

```sh
terraform destroy
```

This deletes the resources. The Key Vault is soft-deleted rather than purged; its name carries a
random suffix, so a fresh `apply` generates a new name instead of colliding.
