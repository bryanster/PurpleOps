# Azure Container Apps (Terraform)

A fully worked Terraform example that deploys Blacklight to
[Azure Container Apps](https://learn.microsoft.com/azure/container-apps/) — Azure's serverless
container service, the Azure equivalent of "Cloud Run".

What it provisions:

| Resource | Purpose |
|---|---|
| Container App (single replica) | Runs the published `ghcr.io/bryanster/blacklight` image |
| Storage Account + Azure Files share | Persistent `/var/lib/blacklight` — the DuckDB database, its WAL and uploaded evidence |
| Key Vault | Holds `BLACKLIGHT_SESSION_SECRET` and `BLACKLIGHT_ENCRYPTION_KEY`, both generated by Terraform |
| User-assigned managed identity | Lets the app read the Key Vault secrets |
| Log Analytics workspace + Container Apps environment | Required base for Container Apps |

The app's two secrets are generated with the `random` provider, stored in Key Vault, and referenced
by the container app through a managed identity — the values never appear in the container app's own
secret list. The only input required from you is an Azure sign-in.

## Prerequisites

- [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli), signed in: `az login`.
- [Terraform](https://developer.hashicorp.com/terraform/install) ≥ 1.5.
- A subscription where you can create resource groups, set Key Vault access policies, and register
  resource providers (Owner, or Contributor with those rights).

The first apply registers the `Microsoft.App`, `Microsoft.OperationalInsights` and
`Microsoft.Storage` providers if your account can. To do it once up front:

```sh
az provider register --namespace Microsoft.App
az provider register --namespace Microsoft.OperationalInsights
az provider register --namespace Microsoft.Storage
```

## Deploy

```sh
cd deploy/terraform
az login
terraform init
terraform apply
```

`terraform apply` creates everything and prints the URL:

```
app_url = "https://blacklight.<env>.<region>.azurecontainerapps.io"
```

Copy `terraform.tfvars.example` to `terraform.tfvars` first if you want to change the region, app
name, image tag, or container size.

## Create the first administrator

A fresh deployment has no users and no sign-up (see `docs/deploy.md`). The first admin is created
with `blctl user create`, which needs exclusive access to the database — DuckDB gives the file to one
process at a time. On Container Apps that means stopping the app, running `blctl` once against the
same file share, and starting it again:

```sh
# 1. Stop the app (scale to zero), releasing the database lock.
az containerapp update --name blacklight --resource-group blacklight-rg \
  --min-replicas 0 --max-replicas 0

# 2. Run blctl once in any container that mounts the same share at /var/lib/blacklight.
#    A one-off Container Apps Job in the same environment is the cleanest way
#    (see "Use storage mounts" and "Jobs" in the Container Apps docs). The command is:
printf '%s' "$PASSWORD" | blctl user create --email you@example.com --name "Your Name" --admin

# 3. Bring the app back to its single replica.
az containerapp update --name blacklight --resource-group blacklight-rg \
  --min-replicas 1 --max-replicas 1
```

The resource group and app name are `name` and `name-rg` from `variables.tf` — `blacklight` and
`blacklight-rg` by default.

## Backups and upgrades

`blctl backup` and `blctl migrate` have the same single-process constraint: stop the app, run the
command against the same share, start it again. Back up the Key Vault secrets too — the session
secret and encryption key live there, not in the container, and a restored database without its
encryption key is one where nobody with MFA can sign in.

To upgrade, change `image_tag` and run `terraform apply`.

## Caveats

- **Single replica is load-bearing.** DuckDB allows one process per database file, so the app is
  pinned to `min_replicas = max_replicas = 1`. Do not scale it out — a second replica would contend
  for the shared database.
- **DuckDB on a network filesystem.** Azure Files (SMB) is a managed, network-attached filesystem;
  DuckDB is designed for local disks and discourages database files on network filesystems. The
  single-replica constraint keeps the access pattern to one exclusive holder, which is the same
  assumption the compose deployment makes on a named volume. For heavy or latency-sensitive use,
  test before trusting it in production.
- **`/dev/shm` is an EmptyDir mount.** Container Apps fixes `/dev/shm` at 64 MiB, which starves
  Chromium during PDF rendering. The example mounts an EmptyDir over `/dev/shm` to give it the
  replica's ephemeral disk instead.
- **No scale-to-zero.** The app runs with a minimum of one replica because the database is stateful
  and single-writer, so there is always an instance running (and billed).
- **Secrets are in Terraform state.** The `random_password` values are generated by Terraform and so
  are recorded in state (and in Key Vault). Treat the state file as sensitive, as always.

## Teardown

```sh
terraform destroy
```

This deletes the resources. The Key Vault is soft-deleted rather than purged; its name carries a
random suffix, so a fresh `apply` generates a new name instead of colliding.
